# 规章制度问答前端：设计评估与实施

## 对现有方案的评估

原方案强调答案可追溯、条款原文和时间适用性，这与后端能力及业务风险相符。但原方案将计划中的能力写成了现成能力：`/api/conversations`、`/api/chat`、制度列表和详情接口均不存在；`/policy-answer` 当前接受表单并一次性返回 JSON，没有 SSE、停止生成或继续生成接口。因此，直接照搬路由、会话、流式输出和制度详情链接会形成无法工作的界面。

此外，回答的 `citations` 使用 `evidence_id`（如 `E1`），不是方案中的数字序号；`requires_human_review` 是后端判断，页面应如实展示。制度的效力和适用日期可能未知，不能默认标为“有效”。原方案中的示例制度、金额和条款也不能冒充真实检索结果。

## 已落地

- 沿用现有 `/policy-qa`，无需新增前端构建与部署流程。页面模板、样式与交互分别位于 `policy/web_ui/answer.html`、`answer.css` 和 `answer.js`，由 `policy/answer_ui.py` 拼装返回。问答页面优先展示回答与结论；条件和警告可展开，证据保留原文、页码与效力状态。回答中的 `[E1]` 或 `[1]` 可定位到对应证据。
- 问答页采用左侧会话、中间回答与输入、右侧证据的桌面布局；窄屏按阅读顺序排列。首屏只呈现回答和前三条依据，长回答、条件、提示及条款原文按需展开。浏览历史时可逐条切换回答与对应证据。
- 条款检索继续对接 `GET /policy-search`，支持问题、日期和最多十条真实结果。服务端文本通过 `textContent` 写入页面。
- `GET /api/policies` 提供标题、文号、发布部门的分页检索和效力状态过滤；`GET /api/policies/{policy_id}` 返回当前结构版本的完整条款。引用可打开完整制度并定位到条款。
- 制度详情根据真实 `chapter_path` 生成章节目录，并高亮从引用进入的条款。
- `POST /api/conversations`、`GET /api/conversations`、`GET/PATCH/DELETE /api/conversations/{conversation_id}` 提供服务端会话；`POST /api/conversations/{conversation_id}/messages` 生成并保存问答；`POST /api/messages/{message_id}/feedback` 保存“有帮助/没帮助”反馈。匿名浏览器通过 HttpOnly Cookie 访问自己的会话，清除 Cookie 后无法恢复旧会话。
- 错误使用接口返回的 `detail` 呈现；索引未准备好和服务不可用由后端分别返回 409 与 503。

## 仍受当前生成链路限制的功能

当前问答模型使用一次性 JSON 响应，服务端必须在完整结果返回后才能校验结论和引用。因此页面只显示“正在检索制度并生成回答”，不显示假的逐字流式输出或“停止生成”。如果需要真正的逐字流式回答，需重构模型调用、增量 JSON 解析、引用校验及取消传播；否则未经校验的片段可能提前展示为制度结论。原文件下载取决于已入库文件是否具有可安全访问的原始文件地址，本次制度详情使用结构化条款原文。
