# 通用办事流程知识图谱设计

## 目标

基于现有 PDF 制度解析、条款结构化、证据定位、条款检索和人工质检能力，建设面向多类办事事项的流程知识图谱。系统回答的核心问题是：某事项应由谁按什么步骤办理、提交什么材料、受什么条件约束、遇到异常如何处理，以及每项结论依据哪条制度原文。

报销是首期试点事项，用于验证数据模型、抽取链路与人工审核闭环；它不是系统的固定边界。试点通过后，采购、合同、用章、人事等事项按同一模型扩展。

## 设计原则

- 原始 PDF 与原始条款是权威依据；图谱中的任何流程节点和关系都必须能回查到制度名称、条款号、页码和原文证据。
- 先结构化条款，再识别流程候选，再抽取流程元素，最后进入人工审核；不从整份 PDF 直接生成不可复核的流程图。
- 事项域、流程动作和审核规则均应配置化；首期的报销词表不能成为全局代码限制。
- 首期只支持当前有效制度的流程导航。制度生效日期、效力状态和版本字段继续保存，但不建设历史时点问答或自动冲突裁决。
- 模型只能产生候选，不能凭空补充制度未明示的步骤、角色、材料或条件。

## 范围与非目标

首期范围是从 PDF 制度中形成可审核的报销流程图谱，并支持以条款证据检索、浏览和导出。首期需要覆盖日常费用报销、差旅报销及制度中明确规定的退回补件、超标准、特殊审批等分支。

首期不替换现有报销系统，不驱动真实审批流，不自动判定制度间冲突，也不以大模型生成无出处的办事结论。流程图谱表达制度规定的标准路径，业务系统的实际审批状态仍属于外部系统数据。

## 概念模型

### 节点

| 节点 | 含义 | 关键字段 |
| --- | --- | --- |
| 事项 | 用户希望办理的业务类别，例如“日常费用报销” | 名称、事项域、别名、状态 |
| 流程 | 为一个事项组织的完整办理路径 | 名称、适用范围、状态、说明 |
| 步骤 | 流程中的可执行动作，例如“提交报销单”“财务审核” | 名称、动作类型、顺序号、说明 |
| 角色 | 执行或审批步骤的岗位、人员类型或部门 | 名称、角色类型、所属部门 |
| 材料 | 步骤要求的表单、票据或附件 | 名称、材料类别、是否必需 |
| 条件 | 触发、前置或判断规则，例如金额阈值、预算状态 | 表达式文本、条件类型 |
| 时限 | 办理期限、报送时点或审批时长 | 数值、单位、适用说明 |
| 结果 | 成功、退回、补件、付款、归档等流程结果 | 名称、结果类型 |
| 制度条款 | 从 PDF 结构化出的条、款、项 | 条款号、章节路径、页码、原文、制度版本 |

所有由抽取产生的业务节点保留 `evidence_text`、`clause_id`、置信度、审核状态和抽取运行标识。跨条款归并为同一事项、步骤或角色时，也要保存每一条支撑依据。

### 关系

| 关系 | 起点 → 终点 | 含义 |
| --- | --- | --- |
| `has_process` | 事项 → 流程 | 某事项具有某办理流程 |
| `has_step` | 流程 → 步骤 | 某流程包含某个步骤 |
| `next_step` | 步骤 → 步骤 | 标准路径中的下一步 |
| `performed_by` | 步骤 → 角色 | 该步骤由谁执行 |
| `requires_material` | 步骤 → 材料 | 办理该步骤需提交或核验的材料 |
| `has_precondition` | 步骤 → 条件 | 步骤开始前必须满足的条件 |
| `routes_to` | 条件 → 步骤/结果 | 条件成立时的分支去向 |
| `has_deadline` | 步骤 → 时限 | 步骤的时间要求 |
| `produces` | 步骤 → 结果 | 步骤完成后的输出或状态 |
| `exception_to` | 步骤/流程 → 步骤/流程 | 特殊情形、补件、退回或升级审批路径 |
| `based_on` | 任意流程节点或关系 → 制度条款 | 该知识的原文依据 |

`next_step`、`routes_to` 和 `exception_to` 只在原文明确给出顺序、条件或例外时创建；无法从制度直接确认的顺序必须标为待审核，不能由模型推断补全。

## 数据导入与处理链路

```text
PDF 文件
  → 解析为页面与内容块
  → 结构化为章、节、条、款、项，并保留页码与原文
  → 事项域分流（报销为试点，事项域可配置）
  → 流程候选条款与连续原文证据
  → 流程节点、关系和条件候选抽取
  → 自动校验与人工审核
  → 已确认的通用流程知识图谱
  → 条款检索、流程浏览和带依据问答
```

处理失败或证据缺失的记录不得进入已确认图谱，而是保留在待审核队列。每次抽取运行必须可恢复、可重跑，并记录解析器、模型和提示词版本。

## 事项域配置

事项域不能固化在 Python 代码中。每个事项域至少配置：名称、别名/关键词、正向流程信号、直接排除信号、优先制度目录以及启用状态。

报销试点使用“报销、报账、费用结算、报销单、发票、票据、审批、审核、支付、结算”等词作为候选召回信号，但是否入图仍以条款原文和人工审核为准。后续新增采购、合同或用章，只增加事项域配置和抽取样例，不改变通用图模型。

## 报销试点

试点先选取权威且当前有效的报销相关制度 PDF，优先覆盖一个完整路径：申请人提交报销材料、业务或部门审批、财务审核、付款或归档。对于材料不全、超出标准、缺少预算或需升级审批等制度明示情形，作为条件分支或例外路径记录。

人工审核完成后，试点必须能对每个步骤显示：执行角色、所需材料、前置条件、下一步或异常去向，以及支撑它的原始条款和页码。若多份制度规定同一流程，保留各自依据，不自动宣称其中任一规定优先。

## 人工审核与质量控制

沿用现有 CSV 质检闭环，并扩展为三类审核项：

1. 流程候选审核：该条款是否属于目标事项的可执行流程规定。
2. 流程元素审核：角色、材料、条件、时限、动作和结果是否准确且有连续原文证据。
3. 路径关系审核：顺序、分支和例外关系是否由原文明确支持。

首期验收采用人工标注的报销问题集和流程样本集。至少统计：条款结构正确率、流程候选精确率/召回率、节点正确率、关系正确率、带依据流程问题的 Top-3 条款命中率，以及无依据候选比例。任何无法给出条款证据的流程答案均视为不合格。

## 与现有工作区的衔接

现有 `policy` 包继续承担 PDF 条款结构化、流程条款分流、实体关系候选抽取、人工审核、质量报告和跨制度条款检索。当前“报销、差旅、采购”固定词表改为事项域配置；当前的事项、部门、对象、材料、金额、时限和审批动作实体继续保留，并新增流程、步骤、条件、结果和角色等通用节点。

当前关系中的适用对象、办理部门、所需材料、金额标准、时限和审批要求可映射到通用模型；新增顺序、分支、异常与结果关系。现有制度、条款、解析版本和效力字段不删除。

## 交付边界

第一阶段交付一个可审核的报销流程图谱及其质量报告，而不是自动执行的报销工作流。验收通过后，以同一模型和事项域配置扩展至其他制度主题。
